## 〇、执行摘要

| 问题 | 结论 |
|---|---|
| Cline 能否接入模型网关？ | **能，而且零代码改动** —— 纯配置即可 |
| 需要像 WorkBuddy 那样仿真身份头吗？ | **需要**，但只靠 `headers` 配置就能做到，无需新增 `auth` 类型 |
| `jiesou/dsh-cline-free-provider` 能直接复用吗？ | **不能直接用**（它是 dsh 插件、走 harness provider seam，与网关是两条不同路径），**但其身份头常量可直接照抄** |
| 该插件的免费模型判定逻辑正确吗？ | **不正确，且有害** —— 它按 `:free` 后缀过滤，那是 **OpenRouter 档**，不是 Cline 免费桶 |
| 真正的 Cline 免费模型是什么？ | `cline-free/*` 前缀（5 个），ID 形如 `cline-free/deepseek-v4.1-flash` |
| 实测能调通吗？ | **能** —— `cline-free/deepseek-v4.1-flash` 返回 HTTP 200，账户余额 $0.00 |
| 网关现成能力够用吗？ | 路由/映射/落库都够用；但**思维链字段名硬编码**导致 Cline 的思考内容被静默丢弃（缺陷 D5） |

**最关键的三个发现**：

1. **Cline 响应的"非流式"格式是非标准 envelope `{"data":…,"success":true}`**，流式才是标准 OpenAI 格式 → 必须配 `quirks: ["force-stream"]`，否则客户端拿到空响应。这一点**没有任何公开资料提到**，是实测发现的。
2. **`:free` 后缀 ≠ Cline 免费模型**。`:free` 是 OpenRouter 档（走 Cline 时可能扣 Credits）；真正的免费桶是 `cline-free/*`。照抄该插件会导致**误判 + 扣费**。
3. **身份头是强制的**：仅 `X-CLIENT-TYPE` 一个头就能通过（200），完全裸头被拒（403 `only available via Cline product surfaces`）。版本号**不是**硬门禁（`0.0.1` 也能过）。

| `reasoningEffortMap{}` | 档位翻译（:2028-2067） | 恒等透传 |

### 2.2 路由与容错

**候选收敛**（`selectCandidates` :803-828）——**配置列表为唯一权威**，三层：
1. `models` 声明了该逻辑名 → 第一层（`models-declared`）
2. `models` **完全为空** → 按上游目录兜底（`catalog-hit` / `catalog-unknown`）
3. 配了别的但没配这个 → **不是候选**，即使目录里有

层级优先于 priority；层级内 "priority 升序 → 数组顺序"。

**熔断**（:361-492）：连续 3 次失败或首次 401/403 → `open`；退避 `90s→3m→6m→12m→24m→30m`。`breakerAcquire`(:438) 是唯一转换点。

**账户池**：`credit`(402)=账户级 30min｜`session`(401/403)=账户级 60min｜`rate`(429)=**「供应商+账户+模型」级** 90s（:1055-1068）。

### 2.3 通用性边界——接入新供应商要改代码吗

**结论：标准 OpenAI 兼容供应商只需改配置；但有 5 类硬编码会导致必须改代码。**

| 供应商形态 | 成本 |
|---|---|
| 标准 OpenAI 兼容 / 需要 quirks / 模型映射 / 多 Key / **自定义头** | **仅改配置** |
| 端点路径非标准（目录不在 `/models`） | **改代码**（`chatPath`/`modelsPath` 不可配，:531/:3555/:3829/:3167 各自硬编码） |
| 鉴权非 Bearer/x-api-key | **改代码**（`RESERVED_UPSTREAM_HEADERS` :1501 会主动剔除 auth 头） |
| **响应侧思维链字段名非 `reasoning_content`** | **改代码**（否则静默丢失，见 D5） |
| WorkBuddy 同类私有接口 | **改代码**（~450 行） |

## 3. 代码缺陷清单

### 🔴 D1｜熔断器半开名额在 3 条路径泄漏 → 供应商永久失联

`breakerAcquire`(:2360) 置 `half-open`；`breakerIsOpen`(:433) 对**所有**并发请求返回 true，且 **half-open 分支不看时间**。释放只有 `breakerRecordFail`/`Success`。但 `forward()` 有 3 个 return 两者都没调用：

| 行 | 分支 |
|---|---|
| **:2543** | 上游 4xx 且 `accountScoped` 且判账户级失败 |
| **:2580** | 404 且不像"模型不存在" |
| **:2600** | 内容拦截 |

`forwardAnthropicViaOpenAI:3253` 同样只 return 不释放。

**后果**：一旦探测名额被这三类分支吃掉，`state==='half-open'` 恒真 → **该家永久退出路由直到进程重启**（无任何基于时间的兜底）。

代码里已意识到该陷阱（`:2566-2568` 写了注释并加了释放），**但漏了前面 3 个 early return**。

### 🔴 D2｜HTTP 200 + 错误 SSE 的供应商结构性无法熔断

`breakerRecordSuccess`(:2602) 在**所有 2xx** 上先删条目，而 SSE 首事件偷看判定在其后(:2614-2661)。`:2657` 的 `breakerRecordFail` 此时 `breaker.get(id) || {state:'closed',fails:0}`(:451) 取到**全新**条目 → `fails` 恒为 1 → 永不开闸。

对恒回 HTTP 200 + `event: error` 的家（正是 `:2606-2609` 注释记载的 api.chiyi.cc 实测形态），**熔断器完全失效**。
**修法**：`:2602` 移到 SSE 偷看之后。

### 🟠 D3｜半开探测 401/403 直接 30 分钟长熔断，跳过指数退避

`breakerRecordFail`(:455) 的 `immediate=(401||403)`；`:461-462` 的 `long` 分支**完全跳过 `opens` 退避** → 形成"每 30 分钟探一次、失败续 30 分钟"的循环。

### 🟠 D4｜账户池耗尽后反而记供应商级熔断（自相矛盾）

`forwardAnthropicViaOpenAI:3347-3350` 在全部账户失败后按 `lastStatus` 记**供应商级**熔断，与 `:2536-2538` 注释宣称的"账户级失败不计供应商熔断"**直接矛盾**。

更糟：`:3179-3185` 凭据不可用路径**不赋值 `lastStatus`** → 单账户供应商走 `continue` 后循环耗尽 → 判 false → 同样滞留。即 **WorkBuddy 凭据文件缺失即可永久废掉该供应商**。

### 🟠 D5｜思维链字段名硬编码 `reasoning_content` → Cline 思考内容静默丢弃 ★本次实测确认

`reasoning_content` 硬编码 4 处（:1687 / :1714 / :2930 / :3022）：

```js
// :1687 —— 流聚合只认这一个字段名
if (typeof d.reasoning_content === 'string') reasoning += d.reasoning_content;
```

而 **Cline 返回的是 `delta.reasoning` / `reasoning_details`**。

**实测证据**（本次）：

```
=== OpenAI 路径：思维链是否被保留 ===
try1: HTTP 200
   content 长度 = 13
   reasoning_content 字段存在 = False   值长度 = 0
   字段清单 = role, content              ← 思考内容完全消失

=== Anthropic 路径 thinking 块是否被保留 ===
try1: HTTP 200  stop=end_turn
   content 块类型 = text
   是否有 thinking 块 = False            ← 同样消失
```

**不报错、不告警，静默丢弃**。这影响的不只是 Cline——任何用 `reasoning`/`reasoning_details` 的上游（OpenRouter 系）都受影响。

### 🟠 D6｜未脱敏的上游错误体入日志 + 入免鉴权 `/health`

`markAccountFailure`(:1055-1067)：`:1064` 的 `reason` 与 `:1067` 的 log **直接拼 `String(detail)`，未过 `maskSecrets`**(:497-503)。

同文件所有其它上游错误体都脱敏了（:2530/:2655/:3234/:3287/:3346/:539）——**1067 是唯一裸输出点**。

而上游鉴权失败时回显收到的 `Authorization` 是常见实现 → 用户 `DSH_GATEWAY_API_KEY` 可能进日志明文。该 `reason` 还经 `accountPoolSnapshot`(:1111) 被**免鉴权的 `/health`**(:4005) 回给任意本机进程。

**修法（一行）**：两处都改为 `maskSecrets(String(detail||...)).slice(0,120)`。

### 🟠 D7｜`/v1/responses` 路径 quirks 全部失效

`forward()` `:2388` 门控 `if (!rawMode && !isAnthropicPath && !responsesMode)` **显式排除 responsesMode**，而 `applyOpenAIQuirks` 全文件仅 `:2389` 一处调用。故对 `POST /v1/responses`：`stringify-tool-choice` / `force-stream` / `prepend-system` **全不生效**。

### 🟠 D8｜`/health` 免鉴权 + 熔断状态零出口

`/health` 在 `authorized()`(:4011) 之前处理(:4000)，任何本机进程可读：`accounts`（provider id、账户 id、**上游错误体前 120 字符**）、`proxy`（代理 URL + 完整 NO_PROXY）。

**同时熔断器状态完全没有出口**——`breaker` 从未被序列化。用户排查"为什么绕过 priority=1 的家"只能翻日志。这使 **D1/D2 对用户完全不可见**。

### 🟠 D9｜密钥打码在 chat 路径失效

`translateBody`(:1907-1927) 打码**只处理字符串 `content`**(:1918-1921)，**数组形态 content 块完全不处理**；而 `handleMessages`(:3736-3746) 与 `translateResponsesBody`(:1972-1982) 都会处理数组。

→ 同一份会话内容走 `/v1/chat/completions`（块格式）时**不打码**。

> **本次亲历**：用户把 API Key 发到 Web UI，模型侧收到的是 `[token:67]` / `[sha256:49]` —— 正是 R9c 降敏（`desensitizeLongTokens` :2072）的产物。**即"用户发给模型的内容会被网关改写"这个行为是真实存在的**，且如上所述在 chat 块格式下会失效。

### 🟡 D10｜SSE 转发无背压

`:2744` 是唯一写下游数据处：`res.write(...)` 返回值被丢弃，全文件 **`drain` 零命中**。慢客户端 + 快上游时 `res` 内部缓冲无上限增长。

### 🟡 D11｜`readTextWithTimeout` 的 4MB 上限是"读完才截断"

`:3329` `readTextWithTimeout(upstream, 30_000, 4*1024*1024)`；实现 `:1767` `resp.text().then(t => String(t).slice(0,limit))` —— **slice 在读完之后**。无 `content-length` 预检，峰值双份内存。其它调用点 limit 都是 500，唯此一处。

### 🟡 D12｜`/v1/models` 泄露上游真实模型 ID 与供应商拓扑

`:3877` `push(alias.get(id) || id, p.id)` —— 对"未声明模型"的家，**上游原始 ID 原样推出**。`:3864` 的 `owned_by` 直接填 **provider id**。

### 🟡 D13｜`accountPool` 无过期删除 → `/health` 响应体单调增长

只有 set(:1062) / delete(:1073-1074)；`coolEntryUsable`(:1029) 是**懒判定**。键含上游模型 ID（`provider#acct@model`），只增不减。

### 已排除的假设（避免误判）

- **账户 Key 不泄漏到下游**：`:1817-1823` 的 skip 集**包含** `authorization`/`x-api-key`；三个下游 `writeHead` 全是白名单式
- **上游状态码透传安全**：`:2677` 仅在 `if(!upstream.ok)` 守卫**之后**执行
- **`selectCandidates` 位置对齐无误**：`Promise.all` 保序，两个调用点长度恒等
- **`providerTimeoutMs` TDZ 不可达**：4 个调用点全在函数体内

### TODO/FIXME

`src/` 下**无任何 `TODO`/`FIXME`/`HACK`**。代之以**「日期 + 事故编号」注释体系**（`R2`/`R9`/`R20`/`R25`/`P1-7`/`Q1`/`V2`…），每处记现象+根因+日期。唯一明确的未完成事项是 `:491` 自述的"后台恢复探测"优化。

# 第二部分：Cline 接入评估

## 4. `jiesou/dsh-cline-free-provider` 分析

### 4.1 它是什么

| 项 | 值 |
|---|---|
| 包名 | `@jiesou/dsh-cline-free-provider` v0.1.19 |
| 形态 | **dsh 插件**（npm 包，带 `cordis.patch.yml`） |
| 核心机制 | `apply(ctx, config)` 里 `ctx.llm.registerAdapter(['cline'], adapter)` —— 挂到 **harness 的 LLM provider seam** |
| 依赖 | `@deepseek-ai/dsh-llm-pi-ai`、`@earendil-works/pi-ai`、`cordis` |
| 规模 | `src/index.ts` 18373 B（单文件） |

**关键架构差异**：

```
dsh-cline-free-provider：  dsh  →  [插件 provider seam]  →  Cline API
workbuddy（本项目）：       dsh  →  [本地网关 3091]      →  上游 API
```

**两条完全不同的路径**。插件在 **dsh 进程内**注册 provider；网关是**进程外的 HTTP 聚合层**。所以该插件**不能直接搬进网关**。

### 4.2 能复用什么

**① 身份头常量（可直接照抄）** —— `src/index.ts` 的 `buildModels()`：

```js
headers: {
  'User-Agent': 'Cline/3.0.47',
  'HTTP-Referer': 'https://cline.bot',
  'X-Title': 'Cline',
  'X-IS-MULTIROOT': 'false',
  'X-CLIENT-TYPE': 'cline-sdk',
  'X-CLIENT-VERSION': '3.0.47',
  'X-PLATFORM': 'terminal',
  'X-PLATFORM-VERSION': '3.0.47',
  'X-CORE-VERSION': '0.0.66',
}
```

**② 目录字段映射** —— `fetchFreeModels()` 显示 Cline 目录是 **OpenRouter schema**：`context_length` / `top_provider.max_completion_tokens` / `supported_parameters` / `architecture.input_modalities`。这正是网关 `models[]` 条目 `contextWindow` / `maxTokens` / `vision` 的来源。

**③ 错误改写思路** —— 它发现"免费推广结束/区域限制"会以 401/403 返回，被 harness 当 AUTH 吞掉，于是把 envelope 改写成 `[cline <type>] <message>`。**实测确认这个现象存在**（见 5.5）。

### 4.3 ⚠️ 不能照抄的部分（照抄有害）

**① `:free` 后缀过滤是错的**

```js
// 插件的核心过滤逻辑
```

### 5.3 ★ 非标准 envelope（决定性发现）

**非流式**：

```json
{
  "data": { "choices":[…], "created":…, "id":…, "model":…, "usage":… },
  "success": true
}
```

顶层键 = `["data","success"]`，**没有标准的 `choices`**。

**流式**（`text/event-stream`）：**标准** `data: {"id":…,"choices":[{"delta":…}]}` … `data: [DONE]`。

**含义**：必须配 **`quirks: ["force-stream"]`**，让网关走流式再自行聚合。**实测验证有效**：

```
=== 非流式请求（网关加了 force-stream）===
HTTP 200
{"id":"gen_01M362NVXC1JBX58FMMBPE3ZPD","object":"chat.completion",
 "choices":[{"index":0,"message":{"role":"assistant","content":"OK"},"finish_reason":"stop"}],…}
```

客户端拿到的是**干净的标准 OpenAI 响应**。日志：`served cline-deepseek via cline-stream` `status=ok dur=2190ms`。

### 5.4 身份头最小集合（实测）

| 请求头组合 | 结果 |
|---|---|
| 全头（基线） | **200** |
| **仅 `X-CLIENT-TYPE: cline-sdk`** | **200** ← 最小充分集 |
| 仅 `User-Agent: Cline/3.0.47` | 403 |
| 仅 `X-PLATFORM: terminal` | 403 |
| `UA + X-CLIENT-VERSION` | 403 |
| **完全裸头** | **403** `Error 403: cline-free/… is only available via Cline product surfaces` |
| 非 Cline UA + 其余全头 | **200**（UA 不校验） |
| **旧版本号 `0.0.1`** | **200**（版本号不是硬门禁） |
| `X-CLIENT-TYPE: cline-vscode` | 500 `empty response content` |

**结论**：
- **`X-CLIENT-TYPE` 是实际门禁**，值必须是 `cline-sdk`
- UA 内容**不校验**，但**存在性是必需的**（裸头 403）
- 版本号**不是**硬门禁（与某些第三方文档的说法不同，本机实测 `0.0.1` 通过）
- → **把插件的全部 9 个头照抄即可，最安全**
